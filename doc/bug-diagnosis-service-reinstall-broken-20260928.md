## 问题描述

月口径修复后重新打包发布，重装 Windows 服务时：安装脚本提示"**服务已存在**"，但服务**无法启动**。用户卡在"装→已存在→启动失败"的循环里。

原诊断未能核实用户截图。本次复核依据源码、系统状态和日志；下文分别标明已确认的代码行为、复核时的状态快照与仍待验证的历史推断，不将它们视为同一层次的证据。

## 环境信息

- 部署模型：发布目录即部署目录（`F:\GitHubs\ihr-mcp\publish\ihr-mcp-v0.1.0\`），使用 node-windows `1.0.0-beta.8` 及其随附的 WinSW 包装服务。
- 服务标识：显示名称为 `ihr-mcp`；当前依赖生成的服务 ID 为 **`ihrmcp.exe`**，现存 `dist\daemon\ihrmcp.xml` 中 `<id>` 与 `<name>` 可直接核实。
- `scripts/service-install.mjs:32` 传入的 `id: 'ihr-mcp'` 在当前依赖中未生效：`daemon.js:324-328` 按 `name` 生成 `ihrmcp`，`:139-143` 生成 `_exe = ihrmcp.exe`，`:117-119` 将 `_exe` 作为 XML 的服务 ID。
- 历史注册二进制：`publish\ihr-mcp-v0.1.0\dist\daemon\ihrmcp.exe`（System 7045 记录）。事件中的显示名称不能直接当作 `sc.exe query` 所需的服务 ID。
- 用户描述的操作链：`publish.cmd` 重打包 → 尝试重装/启动 → 提示已存在或启动失败。各次操作的准确顺序和返回值未完整留存。

### 文件与依赖核验

- 部署目录的 `ihrmcp.exe`、`ihrmcp.xml`、`ihrmcp.exe.config` 最后修改时间均为 **16:55:16**；ZIP 为 **16:46:36**。该时间关系支持守护文件在打包后被写入的推断，不能证明 SCM 注册成功或失败原因。

- 仓库 `dist\daemon\ihrmcp.xml` 指向仓库的 `dist\index.js`，属于此前配置回写仓库问题的相关证据。
- 仓库与发布目录的 `node-windows/lib/daemon.js` SHA-256 一致，本次对依赖的源码结论适用于两处。

### 复核时的状态快照与分支验证

- `sc.exe query ihr-mcp`、`sc.exe query ihrmcp.exe` 均返回 1060；`sc.exe qc ihrmcp.exe` 同样返回 1060。
- 按服务名、显示名称及二进制路径枚举 `Win32_Service`，未发现关联服务。这支持**复核时**注册不存在，不能倒推 16:55 的状态，也不能确定由哪次卸载清除。
- 部署 daemon 三个文件仍在；部署 `config.json` 存在，`mapping.json` 不存在。
- 使用当前依赖及现有文件读取 `Service` 属性，结果为 `id=ihrmcp`、`_exe=ihrmcp.exe`、`exists=true`。以替代日志与事件接收器执行安装前置分支，得到 **`alreadyinstalled`**；未调用真实安装、启动或卸载命令。
- 在模拟 `exists=false` 的对象上验证卸载前置分支，得到 **`alreadyuninstalled`**，确认其会跳过 SCM 清理。
- 对 `service-install.mjs` 使用内存中的配置、命令和 Service 替身，模拟端口被占用且安装判定为已存在。调用轨迹为 `netstat → taskkill → 创建 Service → install/alreadyinstalled`，确认状态判定晚于强杀动作。命令均被替换，未实际结束进程。

## 第三步：调用链与依赖分析

```text
重打包：publish.cmd → scripts/publish.mjs
  ├─ :33-35 检测 daemon 目录 → 仅提示打包后重启，未检查真实注册与运行状态
  ├─ :38-44 删除 stage → 若注册指向此处，删除成功后会留下缺少二进制的注册
  ├─ :50-58 复制 dist，排除仓库 daemon → 部署 daemon 不会由此恢复
  └─ :78-103 还原 config/mapping 后检查它们必须不存在 → 有配置时自检失败

重装：service-install.cmd → scripts/service-install.mjs → node-windows Daemon
  ├─ service-install.mjs:17-28 先结束占用端口的 PID，未检查 SCM 或进程归属
  ├─ daemon.js:752 exists 仅检查 exe/xml
  ├─ exists=true → :514-516 alreadyinstalled → 即使 SCM 无注册，也不执行安装
  └─ exists=false → :533-538 写入守护文件并执行 WinSW install
       └─ 回调忽略错误 → emit('install') → 项目打印成功并调用 service.start()
          此行为不证明安装或启动实际成功

卸载：service-uninstall.cmd → scripts/service-uninstall.mjs → node-windows Daemon
  └─ daemon.js:584-587 exists=false → alreadyuninstalled → 不清除残留 SCM 注册
```

以上是已确认的代码分支关系，不是对每次历史操作顺序的完整重放。

### 影响范围评估

- **全新部署**：无历史注册、无残留 daemon 且 ZIP 不含本机 daemon 时，不受本次状态不一致机制影响；不能据此保证所有安装前提均满足。
- **同一路径就地部署 + 同版本号重打包**：若已注册服务指向该 stage，且删除成功、守护未恢复，会留下缺少二进制的注册。运行中删除还可能因文件占用失败或只完成部分更新。
- **版本号改变**：stage 目录名随版本号变化。旧服务通常仍指向旧目录，不会自动切换到新版本；旧目录的数据与 daemon 不会自动迁移到新目录。
- **从仓库根目录安装**：守护和脚本路径位于仓库，关联配置回写问题仍需按前序报告处理；本次 publish 只清理 stage，不删除仓库 daemon。

| 维度 | 场景 | 当前行为或风险 | 修正要求 |
|------|------|------|------|
| 状态判定 | 注册在、文件缺失 | 卸载被跳过；重装可能对已有注册再次安装 | 按真实服务 ID 和 ImagePath 识别并恢复，不能依赖 `exists` |
| 状态判定 | 注册无、exe/xml 在 | 安装报告 `alreadyinstalled` | 确认无关联注册后备份移走孤立 daemon，再生成新守护 |
| 标识 | 仅查询显示名称 `ihr-mcp` | 1060 可能被误读为服务不存在 | 查询 `ihrmcp.exe`；兼容候选名时分别查询，并核对实际路径 |
| 目录归属 | 同名服务指向其他目录 | 仅凭名称或目录存在性可能保留错误守护或操作其他部署 | 比较 SCM ImagePath 与预期守护绝对路径，不匹配时停止自动处理 |
| 自检 | 还原配置/daemon 后检查它们必须不存在 | 健康部署文件被判定为发布包污染 | 在还原本机文件前完成发布内容检查；确认 ZIP 不含这些文件 |
| 异常退出 | 删除、复制、npm ci、压缩或自检中途失败 | 后续还原不会执行，可能丢失配置/守护或留下不完整应用 | 备份先于删除；覆盖可处理失败的还原路径，保留失败退出码 |

| 上游分支 | 修正 `missing.length` | 文件缺失时仍绕过外层分支，事件也不执行修复 | 不将此修改作为本问题的解决方案 |
| 路径变化 | 版本号改变、Node 路径变化或旧 XML 指向错误目录 | 原样保留可能继续运行旧代码或错误路径 | 明确重新安装/迁移边界，校验 XML 关键路径 |

## 总结与建议

**诊断结论**：已确认“重建部署目录会删除 daemon”“node-windows 按文件判断安装状态”“安装回调未校验错误”三个代码缺陷。它们能形成启动失败与重装受阻的机制，但历史每次失败的准确触发顺序尚未完整证实。另有服务 ID 混用和发布自检顺序错误，需要在修复中处理。`invalidinstallation` 是附带缺陷，不是可依赖的修复兜底。

### 立即恢复（无需改代码，操作前重新核对现场）

先查询实际服务 ID `ihrmcp.exe`，必要时兼容查询 `ihr-mcp`，并通过 SCM 枚举与 `sc.exe qc <实际服务ID>` 核对关联注册和 ImagePath。查询失败只有明确的 1060 才表示该 ID 不存在，权限等其他错误不能视为未安装。运行现有安装脚本前还需确认配置端口无占用；若有占用，先核实归属并有序停止目标实例，无关或归属不明的进程应保留并中止安装，避免现有脚本按端口强杀。

| SCM 与文件状态 | 处理方式 |
|------|------|
| 无关联注册，exe/xml 残留（本次复核快照） | 确认无相关进程占用后，将部署目录的 `dist\daemon` 备份移到该路径之外，再从部署目录运行 `service-install.cmd`。保留 config/mapping；让安装程序重新生成守护。 |
| 注册存在且指向本目录，守护文件缺失 | 确认服务停止，按实际服务 ID 使用 SCM 清理残留注册（如 `sc.exe delete <实际服务ID>`），等待查询返回 1060；移走残留 daemon 后重新安装。此时不能指望 `service-uninstall.cmd` 清理注册。 |
| 注册存在且指向本目录，守护文件齐全 | 先检查 XML 路径、服务状态和启动日志；需要重装时，在文件仍齐全的情况下卸载，并验证真实注册已消失。再检查 exe/xml 是否残留，若有则按“无关联注册、文件残留”处理，然后安装。 |
| 无关联注册、无 daemon | 从目标部署目录正常安装，并核验注册、路径、启动状态和管理页。 |

若同名服务指向其他目录，应先明确要保留或迁移的部署，不能直接删除注册。安装后的成功标准是实际服务状态、ImagePath、XML 脚本路径及管理页均正确，不能仅依据“安装成功”控制台文本。

临时规避流程是：**打包前**在守护尚完整时卸载并确认注册消失，备份部署配置，打包完成且发布内容验证通过后重新安装。现有发布脚本仍有自检及失败还原缺陷，不能将此流程描述为对所有打包失败都有效。

### 方案 A：保留有效部署的守护与配置，防止重打包再次破坏服务

方向可行，但不能直接照搬当前 config/mapping 的还原位置。实施要求如下：

1. 使用真实服务 ID 查询 SCM，确认 ImagePath 指向当前 stage，并检查 XML 的服务 ID、脚本及运行时路径。仅有 daemon 目录不代表服务已安装；孤立、缺失或路径错误的守护应先进入恢复流程。
2. 重建前确认关联服务已停止；未停止或无法确认状态时，中止打包并给出指引。备份及还原不能保证运行中替换安全。
3. 在删除 stage 之前完成备份；config/mapping 分别判断是否存在，守护备份位于 stage 之外。仅保留经过校验的守护运行文件，不将日志或其他机器的 daemon 当作发布内容。
4. 保留仓库 daemon 排除逻辑。在纯净 stage 上构建和检查发布内容、生成 ZIP，确认 ZIP 不含本机配置及 daemon，之后再还原本机配置与守护。修正现有“先还原、再要求文件不存在”的自检顺序。
5. 覆盖删除、复制、依赖安装、压缩、自检等可处理失败的还原路径；显式退出不得绕过还原，原失败仍须通过非零退出码报告。守护和配置还原不代表应用文件已完整回滚，失败后应保持停服，确认部署完整后再启动。强制终止或断电不承诺由普通异常处理自动恢复，备份应可人工取回。
6. 明确方案只针对同一路径重打包；版本目录变化、Node 路径变化或守护配置已被污染时，需要迁移或重新安装，不能盲目原样保留。

### 方案 B：修正安装/卸载的真实状态判断，恢复已有不一致状态

应与 A 配合，覆盖 `scripts/service-install.mjs`、`scripts/service-uninstall.mjs` 的状态检查及结果验证，必要时同步服务管理脚本中的状态查询。
